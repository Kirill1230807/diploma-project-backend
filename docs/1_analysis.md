## 1.2. Аналіз існуючих аналогів та обґрунтування напряму розробки

Для обґрунтування архітектурних рішень розроблюваної системи виконано порівняльно-технічний аналіз трьох широко розповсюджених в індустрії програмних продуктів: Telegram, Viber та WhatsApp. Аналіз зосереджено на оцінці їхніх системних характеристик, використаних протоколів, систем управління базами даних (СУБД) та інженерних обмежень.

### 1.2.1. Telegram

* **Архітектурний патерн та масштабованість:**
* *Патерн:* Розподілена модульна монолітна архітектура з елементами подієво-керованого та сервіс-орієнтованого підходів. Функціонує на базі кастомного низькорівневого мережевого рушія MTProto (бінарний протокол поверх TCP/UDP).
* *Вплив на масштабованість:* Застосування асинхронного неблокуючого I/O (epoll/kqueue) у поєднанні з жорстким шардингом за ідентифікатором користувача дозволяє обробляти значний обсяг паралельних з'єднань на один вузол (вирішення проблеми C10M). Архітектура орієнтована на горизонтальне масштабування кластерів дата-центрів із централізованою маршрутизацією сесій.


* **Протоколи передачі даних та взаємодії:**
* *Клієнт-сервер:* MTProto v2.0 поверх TCP (з можливістю використання HTTP/HTTPS як резервного каналу). Забезпечує бінарну серіалізацію даних (TL-схема), мінімальне оверхед-навантаження та мультиплексування запитів у межах одного з'єднання.
* *Міжсервісна взаємодія:* Кастомні RPC-механізми на C++, що функціонують у внутрішній мережі дата-центрів без використання стандартних високорівневих протоколів (gRPC/REST).


* **Базовий стек даних та консистентність:**
* *СУБД:* Пропрієтарні In-Memory Key-Value сховища (на базі KPHP/Memcached) з асинхронною персистентністю на диск. Для структурованих метаданих застосовуються модифіковані NoSQL та реляційні рушії.
* *Консистентність:* Модель Eventual Consistency для публічних каналів і міжпристроєвої синхронізації. Модель Strict Consistency застосовується локально в межах шарду користувача для збереження послідовності повідомлень.


* **Критичні інженерні недоліки (Technical Bottlenecks):**
* *Відсутність E2EE за замовчуванням:* Базові хмарні чати (Cloud Chats) зберігають ключі шифрування та вміст повідомлень на серверній інфраструктурі. Наскрізне шифрування (Secret Chats) обмежене конфігурацією «точка-точка» і не підтримує синхронізацію між кількома пристроями через відсутність серверної централізованої черги ключів.
* *Кастомна криптографія:* Протокол MTProto використовує власні криптографічні примітиви, верифікація безпеки яких ускладнена порівняно із загальноприйнятими галузевими стандартами (зокрема Signal Protocol).



### 1.2.2. Viber

* **Архітектурний патерн та масштабованість:**
* *Патерн:* Мікросервісна та подієво-керована архітектура (Event-Driven Architecture), орієнтована на обробку голосового трафіку (VoIP) та передачу повідомлень.
* *Вплив на масштабованість:* Компоненти системи декомпоновані за доменами: сигналінг (VoIP), доставка текстових повідомлень, сповіщення та обробка медіаконтенту. Це дозволяє забезпечити ізольоване горизонтальне масштабування високонавантажених сервісів доставки повідомлень незалежно від медіасерверів.


* **Протоколи передачі даних та взаємодії:**
* *Клієнт-сервер:* Кастомний бінарний протокол поверх TCP-з'єднання для сигналінгу та чатів. Для VoIP-викликів застосовуються стандарти SIP, WebRTC, SRTP та механізми обходу NAT (ICE/STUN/TURN).
* *Міжсервісна взаємодія:* Подієва шина на базі RabbitMQ/Kafka, а також gRPC та внутрішній REST API для синхронних міжсервісних запитів.


* **Базовий стек даних та консистентність:**
* *СУБД:* Гібридний стек SQL та NoSQL рішень. Couchbase / MongoDB використовуються для збереження сесій та черг повідомлень, Couchbase/Redis — як In-Memory кеш статусу присутності, RDBMS (PostgreSQL/MySQL) — для обробки білінгових транзакцій.
* *Консистентність:* Шардинг із реплікацією Read/Write на базі моделі Eventual Consistency для черг повідомлень; Strict Consistency — для транзакційних білінгових операцій.


* **Критичні інженерні недоліки (Technical Bottlenecks):**
* *Затримка міжпристроєвої синхронізації:* Зважаючи на прив'язку акаунту до номера телефону та генерацію основних ключів на мобільному пристрої (Master-device), синхронізація з додатковими клієнтами виконується шляхом ретрансляції через сервер. При втраті зв'язку з Master-пристроєм спостерігається розсинхронізація сесій та зростання Delivery Latency.
* *Ресурсомісткість VoIP-інфраструктури:* Медіасервери потребують значних обчислювальних потужностей для ретрансляції RTP-потоків та транскодування мультимедіа в умовах нестабільного мережевого з'єднання, що підвищує вартість утримання інфраструктури.



### 1.2.3. WhatsApp

* **Архітектурний патерн та масштабованість:**
* *Патерн:* Розподілена акторна архітектура (Actor Model) на базі платформи Erlang/OTP (Elixir).
* *Вплив на масштабованість:* Кожен користувач або сесія чату ізольовані в межах легковагого процесу Erlang, що забезпечує низький оверхед оперативної пам'яті на з'єднання та високу стійкість до збоїв (Fault Tolerance). Система масштабується шляхом динамічного додавання нових вузлів (Erlang Nodes) у кластер.


* **Протоколи передачі даних та взаємодії:**
* *Клієнт-сервер:* Модифікований протокол XMPP із бінарним кодуванням (FunXMPP) поверх постійного TCP-з'єднання (WebSockets/Custom Sockets).
* *Міжсервісна взаємодія:* Внутрішній розподілений протокол Erlang Distributed Node Communication та Thrift/gRPC для взаємодії з інфраструктурними сервісами Meta.


* **Базовий стек даних та консистентність:**
* *СУБД:* Mnesia (розподілена In-Memory/On-Disk БД Erlang) для маршрутизації сесій, RocksDB/MySQL (шардована база) — для облікових записів, Cassandra/Blob Storage — для тимчасового збереження недоставлених зашифрованих пакетів.
* *Консистентність:* Strong Consistency в межах актора доставки та Eventual Consistency для розподіленого кешу сесій. БД виконує роль черги прямого скидання (Store-and-Forward).


* **Критичні інженерні недоліки (Technical Bottlenecks):**
* *Обмеження Store-and-Forward у мультидевайс-конфігурації:* Реалізація Signal Protocol для кількох пристроїв (Multi-Device E2EE) вимагає від сервера дублювання зашифрованого повідомлення для кожного зареєстрованого публічного ключа пристроїв сесії. Це спричиняє зростання вихідного трафіку (Bandwidth Amplification) та підвищення навантаження під час трансляції в групові канали.
* *Складність кастомізації Erlang VM:* Вузький профіль експертизи для обслуговування платформи та ускладнена інтеграція з CPU-bound системами (обробка медіа, ML), що вимагає використання винесених C/C++ NIFs (Native Implemented Functions).

### 1.2.4. Аналітичний висновок підрозділу 1.2

Проведений порівняльно-технічний аналіз архітектурних рішень провідних систем обміну повідомленнями виявив низку системних обмежень та інженерних вузьких місць (bottlenecks). Зокрема, використання монолітних структур та пропрієтарних протоколів (MTProto у Telegram) без наскрізного шифрування за замовчуванням створює ризики компрометації даних на боці сервера та ускладнює формальну верифікацію криптографічної стійкості. Архітектурна залежність від Master-пристрою (Viber) призводить до підвищення Delivery Latency та розсинхронізації сесій під час міжпристроєвого обміну, тоді як модель Store-and-Forward у поєднанні з Multi-Device E2EE (WhatsApp) зумовлює вибухоподібне зростання вихідного мережевого трафіку (Bandwidth Amplification) під час трансляції повідомлень у групові канали через необхідність дублювання шифротекстів для кожного публічного ключа пристрою.

Для усунення зазначених архітектурних дефектів та забезпечення вимог до надійності корпоративного сегмента у розроблюваній системі запропоновано комплексний інженерний підхід. Реалізація відкритого та верифікованого криптографічного протоколу Signal Protocol (libsignal) у поєднанні з принципом Zero-knowledge server гарантує конфіденційність передачі даних: серверна частина оперує виключно зашифрованими payload-пакетами та метаданими, унеможливлюючи доступ до вмісту повідомлень на рівні інфраструктури. Використання асинхронного протоколу WebSocket/STOMP у зв'язці з Redis Pub/Sub для горизонтального масштабування сесій дозволяє мінімізувати мережевий оверхед порівняно з традиційними HTTP/REST-запитами та забезпечити затримку доставки в межах декількох мілісекунд у режимі реального часу.

Обраний технологічний стек серверної (Kotlin / Spring Boot / PostgreSQL / Redis) та клієнтської частин (Kotlin / Jetpack Compose / MVVM / Clean Architecture) забезпечує високий рівень модульності, високу щільність типізації та ізоляцію предметної області. Використання апаратного сховища ключів Android Keystore System у сукупності з локальною БД Room повністю вирішує проблему безпечного збереження криптографічних примітивів на клієнтському пристрої. Сформована архітектурна концепція усуває критичні недоліки аналогів, створює базис для побудови масштабованої self-hosted інфраструктури та слугує безпосереднім підґрунтям для етапу детального проєктування компонентів системи у Розділі 2.
